# ai-chat-native 项目评审报告

- **评审基线**：`main` @ `88ddbe9`（v1.1.9 / versionCode 119）
- **评审范围**：`app/src/main/java` 全部 133 个 Kotlin 文件（23,419 行）、46 个单测文件（5,721 行 / 333 例）、2 个 instrumented 测试文件、Gradle 与 CI 配置
- **评审方式**：静态阅读 + 关键路径取证（不含运行时 profiling）
- **本报告只给结论与依据，不改任何代码**

## 0. 一页结论

这是一个**工程质量明显高于"个人自用 app"平均水平**的项目：数据层幂等、协议层有逐字节 golden、网络层有真 socket 的流式测试、323+ 单测全绿。它的短板不在"写得好不好"，而在**三处结构性欠债**——重复的抽象层、为兼容旧 JS 而过度设计的持久化、以及 UI 层的状态粒度。

| 维度 | 评分（10 分制） | 依据 |
|---|---|---|
| 协议/网络层 | **8.5** | 三家协议 + 流式 + 402 降级 + 取消，`ProviderStreamTest` 用真 socket 覆盖字节切分 |
| 数据持久化 | **8.0** | oplog + 快照 + 幂等压缩，多设备 lamport 冲突合并；代价是复杂度极高 |
| 领域逻辑（RP / 记忆 / 检索） | **7.0** | 语义与旧版逐行对齐，但检索分词对中文有实际缺陷（见 3.1） |
| 架构整洁度 | **6.0** | 三套并存的 JS 语义层、三个 700+ 行 god file、模型层用 `extras` 兜底 |
| UI 实现 | **6.5** | 视觉已贴近目标，但状态粒度粗、单文件过大、缺交互测试 |
| 可测试性 | **7.5** | 单测扎实；instrumented 测试 8 例中 3 例是坏的且不在 CI 里 |
| 可维护性 | **6.0** | 注释写得好（这很难得），但注释里大量"对应旧 JS 第 N 行"的耦合说明未来会腐烂 |

**如果只做三件事**：修 3.1 的中文检索（半天，收益最大）→ 拆 5.1 的流式状态（一天）→ 合并 2.1 的三套 Js（两到三天，净删约 700 行）。

## 2. 架构层：三个结构性问题

### 2.1 【P0】三套并存的「JS 语义层」

同一个概念——"让 Kotlin 表现得像 JS"——被实现了三次：

| 实现 | 行数 | 值模型 | 使用者 |
|---|---|---|---|
| `com.aichat.app.plugins.js.Js` | 364 | `typealias JObj = LinkedHashMap<String, Any?>` | 生产代码（1 处 import，实际大量同包使用） |
| `com.aichat.app.net.Js`（`JsCompat.kt:16`） | 263 | `kotlinx JsonElement` | 生产代码 2 处（`DefaultChatEngine`、`FileContext`） |
| `com.aichat.app.data.json.Js` | 376 | 自定义 `class JsObj` | **仅测试**（`Golden.kt`、`StoreRegressionTest`） |

三份实现的 API 高度重叠但不完全一致：

```kotlin
// plugins/js/Js.kt:28
typealias JObj = LinkedHashMap<String, Any?>

// net/JsCompat.kt:16
object Js { fun str(v: Any?): String = ... }

// data/json/Js.kt:29
class JsObj() { private val map = LinkedHashMap<String, Any?>(); ... }
```

**为什么这是 P0**：这不是审美问题，它已经造成过真实 bug，而且会继续造成。项目里反复出现的 `"null"` / `"undefined"` 字符串问题，本质就是三套实现里「`null` 怎么转字符串」的语义不一样：

- `plugins.js.Js.str(null)` → `"undefined"`（踩过两次：世界书面板显示 `null`、校准 key 拼成 `p|m|undefined`）
- `net.Js.str(null)` → 另一套规则
- `data/json.Js.toStr(null)` → 第三套

于是每个调用点都得自己写防御：

```kotlin
// RpMemoryCore.kt: 因为 Js.str(null) 不可靠，到处要私有 wrapper
private fun sv(v: Any?): String {
    val s = Js.str(v)
    return if (s == "undefined" || s == "null") "" else s
}
```

这种 wrapper 在 `RpMemoryCore`、`Affect.kt`、`RpCacheCore` 里各写了一份。

**另一个隐性代价**：`JObj`（`LinkedHashMap`）与 `JsonObject` 是两种类型，跨界要来回序列化：

```kotlin
// ChatController.save 链路上真实存在的往返
codec.loadJs(fs, id)?.let { Js.toJsonObject(it) }?.let(ConversationCodec::decode)
// 反过来
ConversationCodec.encode(c) → KeyOrder.align(json, Js.toJson(prev)) → codec.commitJs(fs, Js.fromJson(json) as JsObj)
```

一次保存，JSON 在 `JsonObject ⇄ JObj ⇄ String` 之间至少过 3 遍。

**建议**：保留 `plugins.js.Js`（`Map` 形态，最贴近 JS，改造成本最低），把它下沉到独立的 `:core-js` 模块或 `com.aichat.app.js` 包；`net.Js` 只保留 HTTP 相关的 4 个函数并委托给它；`data/json` 那套改成 golden 比对专用的 `JsonElement` 视图。**净删约 600–700 行，同时消灭一类 bug。**

### 2.2 【P1】为了「字节对齐旧 JS」而付的持久化复杂度

`FileChatRepository.saveLocked()` 里有两段代码，单独看每一段都很聪明，合在一起说明架构选错了：

```kotlin
// Repositories.kt:98
private fun saveLocked(c: Conversation) {
    var json: JsonElement = ConversationCodec.encode(c)
    val prev = codec.engine.session(store, c.id)?.last ?: codec.loadJs(fs, c.id)
    if (prev != null) {
        // 键序与上次 load/commit 的结果对齐，避免 JSON.stringify 判等产生无意义的 msg.edit
        json = KeyOrder.align(json, Js.toJson(prev))
        json = nullRemovedMessageKeys(json.jsonObject, prev)
    }
    codec.commitJs(fs, Js.fromJson(json) as JsObj)
    ...
}
```

以及 `nullRemovedMessageKeys` 上方那段注释（写得非常诚实）：

> 有意差异 D5：conv-log 的 msg.edit 是 Object.assign 合并，payload 里缺的键不会被删掉——JS 里 `delete m.truncated` 保存，重启回放又会冒出来（JS 本身的潜在 bug）；原生 Codec 省略默认值（truncated:false、vi:0、error:null）也会撞上。

也就是说：**持久化层的 diff 正确性，依赖"Kotlin 序列化出来的键顺序必须和旧 JS 的 `JSON.stringify` 完全一致"**。为了维持这个不变式，引入了 `KeyOrder` 对齐、`nullRemovedMessageKeys` 补救、`oplog` 的 `msg.edit` 语义对齐……

**这在一个单人本地 app 里是不划算的**。它买到的东西是「与旧版数据文件字节级兼容」——而这个目标在 v1.0.1 发版时已经用另一个方案解决了（旧版导出整库 zip → 卸载 → 导入）。

**建议（不紧急，但值得排期）**：把 `ConversationCodec` 的 encode/decode 定为**唯一事实来源**，`commit` 时直接 diff 结构化的 `Conversation`（`data class` 的 `equals`），不再依赖 JSON 键序。`KeyOrder` 和 `nullRemovedMessageKeys` 可以直接删掉。旧数据只需一次性迁移（`StoreMigrationService` 已有）。收益：少一个数量级的不变式。

### 2.3 【P1】领域模型用 `extras: JsonObject` 兜底

```kotlin
// Models.kt:114
data class Message(
    val id: String, val role: Role, val content: String,
    val createdAt: Long = 0,
    val images: List<String> = emptyList(),
    val files: List<JsonObject> = emptyList(),
    val reasoning: String? = null,
    val usage: Usage? = null,
    val error: String? = null,
    val truncated: Boolean = false,
    val finishReason: String? = null,
    val routeSlug: String? = null,
    val versions: List<JsonObject?> = emptyList(),
    val vi: Int = 0,
    val extras: JsonObject = EmptyJson,   // pluginStatus/routeView/sources/knowledgeTrace/_conflicts…
)
```

`extras` 是 5 种以上语义的公共垃圾桶，而且**关键字段藏在里面**：每条消息用的是哪个模型，存在 `extras["model"]`，因为 `Message` 没有 `model` 字段。于是成本计算要这样取：

```kotlin
// ChatMounts.kt
val model = (m.extras["model"] as? JsonPrimitive)?.takeIf { it.isString }?.content ?: conv.model
```

后果：任何一次 encode/decode 丢了 `extras`，历史消息的成本、插件徽章、知识库溯源会**静默消失**——不会报错，只是数字变了。

**建议**：把 `model`、`providerId` 提为 `Message` 的一等字段（两个字符串，迁移成本极低）；`extras` 只留真正的插件私有状态。

## 3. 算法层

### 3.1 【P0，本报告最重要的一条】rpmemory 的 BM25F 对中文实际退化成「整句精确匹配」

`RpMemoryCore` 的检索分词只有一条正则：

```kotlin
// RpMemoryCore.kt:379
private val TERM_SPLIT = Regex("[\\s\\p{P}\\p{S}]+")

fun terms(s: Any?): List<String> =
    Js.str(s).lowercase().split(TERM_SPLIT).map { it.trim() }.filter { it.isNotEmpty() }
```

中文没有空格。所以：

```
"海边有个渔村，灯塔是红色的"
  → ["海边有个渔村", "灯塔是红色的"]        // 只有两个 term
查询 "灯塔"
  → ["灯塔"]                                // df["灯塔"] == 0 → idf 分支直接 return
```

`bm25f()` 里第一行就跳过了：

```kotlin
Q.forEach { (t, qw) ->
    if ((idx.df[t] ?: 0) == 0) return@forEach   // 中文查询几乎全部命中这一行
    ...
}
```

**结论：只要用户不用「原句」检索，rpmemory 的 BM25 通道就返回 0 分。** 实际可用的只剩 `pinned` 条目和 `keywords` 字段的**完全相等**匹配。而 `keywords` 由 `autoKeywords` 生成，同样是 `terms()` 切的，所以关键词也只会是整句。

对比同一仓库里**已经写对了**的那套——知识库用的 `RetrievalCore.grams`：

```kotlin
// RetrievalCore.kt:20
/** term 切分：中文 bigram（单字段落保留单字），英文/数字 [a-z0-9_]+ */
fun grams(text: Any?, n: Int? = null): MutableList<String> {
    ...
    if (isHan(str[i])) {
        val seg = str.substring(st, i)
        if (seg.length == 1) out += seg
        else for (k in 0 until seg.length - (nn - 1)) out += seg.substring(k, k + nn)   // "灯塔是红色的" → 灯塔/塔是/是红/红色/色的
    }
}
```

中文 bigram 之后，「灯塔」就能与「灯塔是红色的」共享 "灯塔" 这个 term，df 不为 0，BM25 正常工作。

**两个同名算法、两套分词、一套对一套错**，这正是 2.1 那种「重复实现」的真实代价。

**修法**（约 30 行）：`RpMemoryCore.terms` 直接委托 `RetrievalCore.grams`。注意 `RpMemoryCore` 的 `W = {"text":1.0,"keywords":1.6}` 权重是在旧分词下调出来的，换分词后需要用 golden 重新校准一次（`tools/rpmemory-golden/gen.cjs` 现成）。同时**必须补中文检索的回归测试**——现在的 786 行 `RpMemoryCore` 有测试，但都是拿英文/或整句当输入，所以这个缺陷一直没被发现。

> 顺带说明这为什么没被真机发现：`selectRelevant` 的另一半逻辑（`pinned` 单独预算 + `decay` 时间衰减 + `OPEN_BOOST`）都是对的，所以面板里"注入了 3 条记忆"看起来很正常，只是注入的永远是置顶那几条。

### 3.2 【P1】两套 token 估算系数互相打架

```kotlin
// RpCacheCore.kt:160 —— 认真的一版，逐码点
/**
 * 本地 Token 估算（DeepSeek 官方换算）：汉字/假名/谚文/全角 0.6、英文字母 0.3、
 * 数字 0.5、ASCII 标点 0.6、空白 0.1、其它码点 1.5，最后向上取整。
 */
fun estimateTokens(text: Any?): Int { ... }

// RpMemoryCore.kt:456 —— 粗的一版
private fun estTokens(e: JObj): Int = kotlin.math.ceil(Js.str(e["text"]).length * 0.7).toInt() + 6
```

同一个预算体系（`memTokens = 600`）里用两把尺子。`length * 0.7` 对中文高估约 17%（0.7 vs 0.6），对英文**高估 133%**（0.7 vs 0.3）——英文记忆条目会被提前截断，注入条数比配置值少一半。

而 `RpCacheCore` 那一版还有校准机制，说明作者自己也知道估算不准：

```kotlin
// RpCacheCore.kt:219
/** 用真实输入 token 校准估算：指数平均（旧值 0.7 + 本轮 0.3），系数夹在 0.5–2.5。 */
fun calibrate(st: JObj, rawEstimate: Int, actualPrompt: Long, meta: JObj?): JObj {
    if (rawEstimate <= 200 || actualPrompt <= 0L) return st
    val ratio = (actualPrompt.toDouble() / rawEstimate).coerceIn(0.5, 2.5)
    ...
}
```

但这个校准**只作用于 rpcache 的分层预算**，没有传导到 rpmemory 的 `memTokens`。

**修法**：`estTokens` 改为 `RpCacheCore.estimateTokens`，并把 `calib` 系数一路传下去（约 10 行）。

### 3.3 【P1】BM25 索引每轮重建，而隔壁有缓存

```kotlin
// RpMemoryCore.kt:396
fun buildIndex(list: List<JObj>): Index { ... }        // 无缓存

// RetrievalCore.kt:41
fun buildIndex(docs: List<JObj>?, fields: List<String>?, prev: Index? = null): Index {
    val sig = ds.joinToString("|") { ... } + "#" + fs.joinToString(",")
    if (prev != null && prev.sig == sig) return prev   // 内容没变就直接复用
    ...
}
```

每条消息都要过一遍 `selectRelevant` → `buildIndex`。记忆条目上限 `maxInject=8` 但候选池通常是几十到几百条，每轮重建的代价是 O(N × terms)。单次可接受，但它是"每条消息都做一次"的固定开销，且明明有现成的 `sig` 短路模式可以照抄。

### 3.4 其他较小的问题

- **中断的请求不记用量。** 服务商不发 usage chunk 时（用户提前停止），这一轮的 token 完全不计入统计。`StreamEvent.UsageUpdate` 只在收到 usage 时触发，没有"按已生成文本估算"的兜底。这会让用量页系统性偏低。
- **`estimateItems` 里图片按固定 1000 token 计**（`RpCacheCore.kt:185`），而三家服务商对图片的计费口径不同（Anthropic 按 (w×h)/750，Gemini 固定 258）。带图对话的预算判断会偏。
- **`Deltas.parseError` 的 `HINTS` 只有 6 个状态码**，且 402 的提示文案在 `DefaultProviderClient` 里又各自拼了一遍（`if (status == 402 && downgraded)`），同一件事有两处判定。

### 4.2 【P1】插件的失败是静默的

```kotlin
// PluginRegistryImpl.kt:58
private inline fun <T> safe(p: ChatPlugin, hook: String, fn: () -> T): T? =
    try { fn() } catch (e: Throwable) { pushErr(p.id, hook, e.message ?: e.toString()); null }

// PluginRegistryImpl.kt:89
cur = try { p.onBeforeRequest(cur, status) } catch (e: Throwable) {
    pushErr(p.id, "onBeforeRequest", e.message ?: e.toString()); continue
}
```

设计上是对的（一个插件崩了不该拖垮整轮对话），但**用户完全看不到**。`pushErr` 只写内存里的 `errors` 列表，没有任何 UI 消费它。

这不是理论问题：世界书"写了不生效"整整一个版本都没被发现，根因就是 `RpCachePlugin.onBeforeRequest` 的闸门 `if (!hasAnyBlock(st0)) return ctx` 直接静默返回，而**没有任何地方告诉用户"你的世界书没起作用"**。

**建议**：`errors` 非空时在顶栏挂一个角标（红色小圆点），点开看最近 20 条 `plugin/hook/message`。约 40 行，能消灭一整类"我以为它生效了"的问题。

| 缺口 | 用户感知 | 工作量 |

### 4.4 一个产品层面的建议

`affect`（好感度）已经改成"按对话启用"，但 `rpcache` 的闸门 `shouldEngage` 仍是"有 RP 块 **或** 有世界书"就启用（这是 v1.0.2 修的）。**建议把这条规则显式化并暴露给用户**：在 RP 检视面板顶部加一行"本对话已启用：缓存分层 / 世界书 / 记忆 / 好感度"，让"为什么这轮 token 变多了"变得可解释。这类"隐式生效"的功能，可解释性比功能本身更重要。

## 5. UI 层

### 5.1 【P0】流式输出导致整屏重组

```kotlin
// ChatScreen.kt:222 —— 在 ChatScreen 根部
val st by controller.state.collectAsStateWithLifecycle()
```

`ChatUiState` 是一个大对象，里面含 `streams: Map<String, Streaming>`。流式期间 `DeltaBuffer` 每 50ms 往 `_state` 里塞一次新状态：

```kotlin
// ChatController.kt:698
_state.update { st ->
    val cur = st.streams[convId] ?: return@update st
    st.copy(streams = st.streams + (convId to cur.copy(text = cur.text + t, reasoning = cur.reasoning + r)))
}
```

因为 `st` 是在**根部**读取的，Compose 无法只重组消息气泡——`Scaffold`、顶栏（标题 + 模型胶囊 + 菜单）、`ModalNavigationDrawer`、输入条全部跟着重组，**每秒 20 次**。`st.streams` 每次还是新的 `Map` 实例，等于没有任何结构相等可以利用。

长对话（几百条消息）+ 长回复（几千 token）时，这是可感知的掉帧来源。

**修法**：把流式文本拆成独立的 flow，只在消息气泡内部读：

```kotlin
// 建议方向
val streamingText: StateFlow<Map<String, Streaming>> = controller.streams   // 独立
// 气泡内
val live by remember(id) { controller.streamOf(id) }.collectAsStateWithLifecycle()
```

同时 `ChatUiState` 里 `streams` 移出，根部的 `st` 就只在消息增删/切换会话时变。**约 80 行，收益是流式期间的帧率。**

### 5.2 【P1】自动滚底会打断阅读

```kotlin
// ChatScreen.kt:274
LaunchedEffect(st.convId, messages.size) {
    if (messages.isNotEmpty()) listState.scrollToItem(0)
}
```

`LazyColumn` 用了 `reverseLayout = true`，item 0 是最新消息。这个 effect 的 key 是 `messages.size`——**只要消息条数变了就强制跳到底部**：

- 正在往上翻历史时，别的会话来了消息（`messages` 是当前会话的，影响较小）
- 删一条消息 → 条数减少 → 跳到底部
- 编辑重发 → 条数变化 → 跳到底部
- 每轮发送（user + assistant 占位各一次）→ 两次跳转

**修法**：只在"用户本来就在底部附近"时才自动滚。

```kotlin
LaunchedEffect(st.convId, messages.size) {
    val atBottom = listState.firstVisibleItemIndex <= 1 && listState.firstVisibleItemScrollOffset < 200
    if (atBottom || newMessageFromMe) listState.animateScrollToItem(0)
}
```

约 20 行，是这轮 UI 里性价比最高的一处。

### 5.3 【P1】三个 god file

| 文件 | 行数 | 里面装了什么 |
|---|---|---|
| `ui/chat/ChatScreen.kt` | 668 | 顶栏 + 空态 + 消息列表 + 输入条挂载 + 模型选择器 + ⋮ 菜单 + 导出 + 6 个对话框的入口 |
| `ui/chat/ChatController.kt` | 730 | 会话生命周期 + 流式状态 + 消息编辑/删除/重生成 + 附件 + RP 状态 + 剪贴板 + toast |
| `data/convlog/JsConvLog.kt` | 865 | oplog 应用 + 快照 + 压缩 + 冲突合并 + 旧格式迁移 + session 缓存 |

三个文件合计占生产代码的 9.6%，但承载了几乎所有的变更热点。**建议**：`ChatScreen` 按 `ChatTopBar` / `MessageList` / `ChatMenus` 拆三个文件（纯移动，不改逻辑，风险极低）；`ChatController` 把"RP 状态相关"和"消息编辑相关"拆成扩展函数或委托类。

### 5.4 视觉与设计 token

`theme/` 里已有 `Palette`（对齐旧版 `app.css` 的颜色）和 `Space`/`Radii`/`Motion`，方向是对的。但实际使用中仍有大量硬编码：

.padding(start = 8.dp)

## 6. 工程与测试

### 6.1 测试分布不均衡

```
写得好：net/（真 socket 流式）、plugins/rp/（golden 对照）、data/（迁移与编解码）
写得好但没人看：golden 资源 53 个 jsonl + 13 个 convlog 夹具
几乎没有：ui/（只有 2 个 androidTest 文件）
```

8 个 instrumented 测试里，**3 个是坏的**：

1. `DeviceRegressionTest.migratedStoreIsCompleteAndBackupRoundTrips` —— 断言"迁移报告对话数 = 索引条数"，但只对**未迁移过**的设备成立；模拟器上已有 `.native-migrated` 标记 → `expected:<2> but was:<0>`
2. `AppRootUiTest.tabSwitchKeepsInputDraft` —— `onNodeWithText("生图", substring = true)` 在 UI 改版后命中 4 个节点
3. `AppRootUiTest.regenerateVersionsAndEdit` —— 定位符 `2/2` / `保存并重新发送` 失效

而且 **CI 从不运行它们**（`.github/workflows/android.yml` 只跑 `:app:testDebugUnitTest`）。等于这层测试既坏又不在关卡上。

**建议**：先修这 3 例（约半天），再按 `reactivecircus/android-emulator-runner@v2` 接进 CI，但**只挂 `main` 分支 + 手动触发**——PR 上跑模拟器会让 18 秒的反馈循环变成 3 分钟，得不偿失。

## 8. 一句话总结

这个项目的技术底盘（协议、流式、持久化、幂等迁移）已经超过了它的用户规模需要的水位，**真正的风险不是"做不出来"，而是"写得太满"**——三套 JS 层、两套分词、两套 token 尺子、700 行的控制器，都是"为了逐字节对齐旧版"这个正确但过载的目标留下的。

下一步最有价值的动作不是继续加功能，而是**合并重复实现 + 让失败可见**。前者减少接下来每次改动的成本，后者让已经存在的功能真正被用户用上。

**健康度判断**

- 技术底盘（协议、流式、持久化、幂等迁移）仍然扎实，49 个单测文件覆盖了编解码、路由、成本、检索、RP、迁移等关键路径。

3. **并行补 CI 门禁**：至少把 `testDebugUnitTest` 接进 GitHub Actions，避免再出现"改动累积无法验证"。
