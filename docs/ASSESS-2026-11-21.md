## 1 T4 · "15:26 全 miss"：是什么 / 怎么定位 / 值不值得修

### 1.1 是什么

PLAN 里 B 段那条"15:26 全 miss"（CSV **07:26:43**，p=11,915 / cached=0 / out=485 / $0.010755）**不是主对话请求**：

- `askModel`（AiChatApp.kt:137-157，插件旁路的唯一通道）发的是**单条 USER 消息、system 空、无 cache_control 断点**的裸请求 —— 与主对话请求的头部（【RP 协议】+ system + 世界块）**零共享前缀**，`cached=0` 是结构性的，不是"前缀被改写"。
- 它的输出指纹（out=485 / reasoning=438）与 12 分钟后独立的旁路调用 07:38:37（p=602 → out=488 / r=454）几乎一致 —— 同一摘要/记忆任务的两次运行；prompt ≈ 指令 + 待摘要批次（批次含整段未摘要历史，才有 ~11.9k 这么大）。
- 主对话行（07:25:25、07:26:26、07:30:58…）前缀连续、全命中；这条旁路行恰好夹在中间，被逐行对表误认成"同一对话只多 602 token 却整段失效"。**"只多 602 token"是两个不同请求的巧合对比，不是一次改写。**

### 1.2 怎么定位（四步证据链）

| 步骤 | 检验 | 结果 |
|---|---|---|
| 0 upstream 切换（PLAN 评审修正后的第一顺位） | 三行 `provider_name` / `variant` | 全部 `Google` / `standard` → **排除** |
| 1 TTL / 新会话 | 07:26:26 命中 11,285 → 17s 后 07:26:43 miss → 07:30:58 恢复 11,285 | 前缀两侧夹逼全命中 → **排除**；"破坏"从未发生 |
| 2 输出指纹 | 485/438 vs 488/454（07:38:37 的旁路调用） | 同一任务的两次运行 → **锁定旁路家族** |
| 3 请求形态 | AiChatApp.kt:146-150 | 单 USER 消息 + system="" + 无断点装饰 → cached=0 结构性必然 → **定案** |

B 段 7 条零缓存的构成（修订 PLAN 的归因）：旁路家族至少 **5 条** —— 06:16:14（p=8,875→out=527）、07:26:43、07:37:45、07:38:06、07:38:37（PLAN 已认出后三条）。剩下 17:36:58（p=4,103 c=0，次分钟 p=4,134 c=4,119）形态是**章节提交后新前缀的首轮**（GCache `commit=true` 设计内），非缺陷。

### 1.3 值不值得修

**不修，T4 关账。**

1. 主对话缓存 99.7% 命中没说谎 —— 唯一"不该发生的 miss"不是主对话的。
2. 旁路家族的正确修法就是 T3：摘要走 GLM（$0.0699/M），11.9k 输入全 miss 也只要 ≈ $0.0016，比任何"改拼装顺序 / 给旁路加断点"的工程便宜一个量级。
3. `trace.conflict` 升级（PLAN T4 第 3 步）**取消**：无槽位冲突证据，ContextSlots 冲突账本维持现状。

**遗留观察（不立项）**：旁路 ask 若要再省，可把指令块放尾部让隐式缓存吃到大批次前缀 —— T3 落地后收益上限 ≈ $0.002/次，不值得排队。
