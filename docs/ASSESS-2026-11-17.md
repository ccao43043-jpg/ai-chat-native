## 0 一页结论

**底盘继续是工厂级，本轮核对的价值不在「发现新功能缺口」，而在发现「计划文件与代码脱节」和「发布链路从未被验证」。**

三句话：

1. **计划文件有 11 处与代码不符**，其中 6 处是「已完成但仍标未做」——和上次误判 D8 是同一个病根（一份事实多个状态列），说明上一轮文档收敛只治了「身份」，没治「状态」。
2. **发布工程是当前最大的空白**：`release` 变体从未构建过（`minifyEnabled false`、无 `proguard-rules.pro`、CI 只跑 `assembleDebug`、`lint { abortOnError false }`）。现在能发版，是因为发的其实是 debug 产物。
3. **用户数据路径上还有两处硬伤**：图片以 base64 内联进消息（一轮 10 图 ≈ 1.4–2.7 MB 进 oplog），而 `data/files`（文件截断）与 `data/backup`（备份往返）**零单测**。

剩余高 ROI 工作约 **4–6 天**可到「敢发 1.6.0」的水平，明细见 §4。

## 2 逐层诊断（含新发现）

### 2.1 发布工程 · **P0（新）**

`app/build.gradle:55-69`：

```groovy
release {
    minifyEnabled false          // 从未打开过
    signingConfig hasKs ? signingConfigs.stable : signingConfigs.debug
}
lint { checkReleaseBuilds false; abortOnError false }
```

- 没有 `proguard-rules.pro`（`app/proguard-rules.pro` **不存在**），R8 从未跑过任何一次。
- CI 只 `:app:assembleDebug`，**release 变体从未被构建验证**。
- `lint` 全部放行，等于没有静态门槛；全仓也没有 detekt/ktlint。

**风险**：一旦真开 R8（或某天要用 AAB 上架），反射/kotlinx-serialization/Compose 的 keep 规则缺失会引发「构建成功但运行时崩」的经典事故；而体积上，现在 11.7 MB 里有大量可裁剪代码与未用资源。

### 2.2 用户数据路径 · **P1（新）**

**(a) 图片内联进 oplog。** `Message.images: List<String>`（`domain/model/Models.kt:119`）存的是 `data:image/jpeg;base64,...`（`ui/image/RefImageLoader.kt:43`，单张压缩上限 4 MB）：

```kotlin
"data:image/jpeg;base64," + Base64.encodeToString(bytes, Base64.NO_WRAP)
```

1024px / JPEG 82 通常 100–200 KB，base64 后 ≈ 140–270 KB。一轮带 10 张参考图 → **1.4–2.7 MB 写进 `conv_<id>.log.jsonl`**，且每次 `commit` 会把它作为 op payload 再序列化一遍。长图会话下会话文件可达数十 MB：加载变慢、内存压力、备份 zip 同步膨胀。

**(b) 关键路径零测试。** 按目录统计 `@Test` 数：

| 目录 | 行数 | 测试 |
|---|---|---|
| `data/files`（`capText` / `buildFileContext`） | 595 | **0** |
| `data/backup`（整库导出/导入） | 75 | **0** |
| `data/secret`（KeyVault / Keystore AES-GCM） | 118 | **0** |
| `ui/common`（Markdown / 编辑器 / 图片） | 1,323 | **0** |
| `ui/image` | 623 | **0** |
| `ui/conversation`（抽屉） | 411 | **0** |
| `plugins/js`（三套语义层之一） | 545 | **0** |

备份与文件截断恰好是「用户会立刻发现坏了、但单测抓不到」的两条路径——`data/backup` 的 `importBackup` 会整库替换，写错一次就是数据丢失。

**(c) `unitTests.returnDefaultValues = true`**（`app/build.gradle:72`）：单测里误调 Android API 会静默返回 `0/null/false` 而不是报错。当前测试确实没调 Android API（已全量扫描 `TextUtils/Uri/Log/os./BitmapFactory`，0 命中），所以现在是「无害但危险」的钩子——建议关掉并确认仍绿。

### 2.3 静默失败 · **P1（新）**

8 处空 catch（`catch (...) { }`）：

| 位置 | 后果 |

### 2.4 国际化 · **P2（新，建议明确不做）**

- `res/values/strings.xml` 只有 **1 条**（`app_name`）。

## 4 改进建议（按 ROI 排序）

### 批次 A · 发布工程补课（0.5 天）

1. 新建 `app/proguard-rules.pro`（kotlinx-serialization / Compose / OkHttp 的 keep 规则）。
2. `release { minifyEnabled true; shrinkResources true; proguardFiles ... }`。
3. CI 加 `:app:assembleRelease`（不进 CI 门禁也行，至少每次 main 构建一次并上传产物）。
4. `lint { abortOnError true; warningsAsErrors false }`——只拦 error，不拦 warning。
5. 验收：`assembleRelease` 通过 + APK 体积对比（预期 11.7 → 7–8 MB）+ 装机冒烟（发送一轮）。

> 这一步不需要上架，纯内部验证；但它是「未来任何一次真发版不炸」的前置条件。

### 批次 B · 用户数据路径补测（0.5 天）

1. 关掉 `unitTests.returnDefaultValues`，全量跑一次确认仍 413 绿。
2. `data/files` 补 `capText` 边界（空串 / 恰好等于上限 / 超大 / 多文件配额）、`buildFileContext` 预算分配。
3. `data/backup` 补导出 → 清空 → 导入往返（含空会话、带图会话、损坏 zip 三种）。
4. 空 catch 补日志/提示（`Affect.kt:163`、`JsConvLog.kt:714`、`PdfText.kt:109`、`ProvidersScreen.kt:195`）。

### 批次 C · 图片外置（1–2 天，改数据层）

- 压缩后写 `img_<sha1>.jpg` 到 store，消息里只存 `img:<sha1>` 键并保留 `data:` 前缀兼容旧数据。
- 读路径：遇到 `data:` 前缀则懒迁移（写 blob → 替换为键 → 下次 commit 生效）。
- 收益：会话文件回到 KB 级、oplog 追加成本可预测、备份 zip 不再指数膨胀、相同图片天然去重（同一张参考图反复用只存一份）。
- 风险：迁移逻辑必须幂等 + 旧版本读到 `img:` 键要能降级（旧版本已发出去过，倒退安装的场景存在）。

### 批次 D · 按既有计划继续（PLAN-ALGO-CACHE）

| 批次 | 内容 | 工时 |
|---|---|---|
| B2 | 预算系数能力表（`BudgetProfile`，开关默认 `legacy`）+ `plan()` 单轮估算 memo | 1.5 天 |
| B3 | D7 文件分块检索替代前缀截断（`files.chunkRetrieval` 开关） | 2–3 天 |
| B4 | 路由埋点 → 观察 → 探索/衰减 | 1–2 天 + 观察 |
| #13 | detekt/ktlint + 3 个 Compose smoke | 1 天 |

### 明确不做（建议写进 MASTER-PLAN）

- i18n / 多语言：1,630 处硬编码中文，收益为零，成本极高。
- 关掉 `usesCleartextTraffic`：会破坏「用户自填 http 网关」这条真实用法。
- 把 `!!` 全改成安全调用：已逐个核对均有保护，纯改风格不划算。
